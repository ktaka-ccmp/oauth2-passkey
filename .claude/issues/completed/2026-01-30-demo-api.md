## Summary

Create a new `demo-api` application that demonstrates Bearer token authentication mode. This API-only demo will be cURL/Postman compatible and showcase the newly implemented `SESSION_AUTH_MODE=bearer` functionality.

## Background

The Bearer token authentication support was implemented in issue 2026-01-23-01. However, the existing demos (`demo-both`, `demo-oauth2`, `demo-passkey`) are browser-based and use cookie authentication. A dedicated API demo is needed to:

1. Demonstrate Bearer token authentication in action
2. Provide cURL/Postman testing examples
3. Serve as a reference implementation for API/mobile client integration

## Scope

### In Scope
- Passkey authentication only (OAuth2 requires browser redirects)
- Bearer token mode (`SESSION_AUTH_MODE=bearer`)
- cURL/Postman compatible endpoints
- JSON request/response format
- Example commands in README

### Out of Scope
- Browser UI
- OAuth2 authentication (requires redirects)
- HTML pages

### 3. API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/health` | Health check |
| POST | `/api/passkey/register/start` | Start passkey registration |
| POST | `/api/passkey/register/finish` | Complete passkey registration |
| POST | `/api/passkey/auth/start` | Start passkey authentication |
| POST | `/api/passkey/auth/finish` | Complete authentication, returns Bearer token |
| GET | `/api/protected` | Protected resource (requires Bearer token) |
| GET | `/api/me` | Current user info (requires Bearer token) |
| POST | `/api/logout` | Invalidate Bearer token |

### 4. Response Format

Authentication success response:
```json
{
  "token": "session_id_here",
  "token_type": "Bearer",
  "expires_in": 600
}
```

Protected resource response:
```json
{
  "user_id": "...",
  "account": "user@example.com",
  "message": "Access granted"
}
```

### 5. Example cURL Commands

```bash
# Start authentication
curl -X POST http://localhost:3002/api/passkey/auth/start \
  -H "Content-Type: application/json" \
  -d '{"account": "user@example.com"}'

# Finish authentication (get Bearer token)
curl -X POST http://localhost:3002/api/passkey/auth/finish \
  -H "Content-Type: application/json" \
  -d '{"response": "..."}'

# Access protected resource
curl http://localhost:3002/api/protected \
  -H "Authorization: Bearer <token>"

# Get current user
curl http://localhost:3002/api/me \
  -H "Authorization: Bearer <token>"

# Logout
curl -X POST http://localhost:3002/api/logout \
  -H "Authorization: Bearer <token>"
```

## Technical Notes

### Passkey Registration Challenge

For API-only passkey registration without browser:
- User must already exist in the database (pre-seeded or created via another method)
- Or provide a separate user creation endpoint

Possible approaches:
1. **Pre-seed users**: Create test users in database at startup
2. **User creation endpoint**: Add `POST /api/users` to create users
3. **Self-registration**: Allow registration with just an account name

### WebAuthn Authenticator

For testing without a browser:
- Use a software authenticator library
- Or document that real testing requires browser-based WebAuthn
- Provide mock responses for demonstration purposes

## Resolution

Implemented demo-api with the following structure:

```text
demo-api/
├── Cargo.toml          # Dependencies on oauth2-passkey core
├── .env.example        # Example environment configuration
├── README.md           # Documentation with cURL examples
└── src/
    └── main.rs         # API implementation
```

**API Endpoints Implemented:**

- `GET /health` - Health check
- `POST /api/passkey/register/start` - Start passkey registration
- `POST /api/passkey/register/finish` - Complete registration (returns Bearer token)
- `POST /api/passkey/auth/start` - Start passkey authentication
- `POST /api/passkey/auth/finish` - Complete authentication (returns Bearer token)
- `GET /api/protected` - Protected resource (requires Bearer token)
- `GET /api/me` - Current user info (requires Bearer token)

**Note:** `/api/logout` was not implemented as session deletion is typically handled differently in Bearer token mode.

**Key Implementation Details:**

- Uses `oauth2-passkey` core library directly (not `oauth2-passkey-axum`)
- Returns `SessionCreationResponse::Bearer { token, token_type, expires_in }` as JSON
- Protected routes use middleware to validate Bearer token via `is_authenticated_basic`
- No CSRF validation needed for Bearer auth
