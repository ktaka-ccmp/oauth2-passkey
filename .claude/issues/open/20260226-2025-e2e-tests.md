## Description

Add browser-level end-to-end tests that exercise the full authentication flow including JavaScript execution, DOM interaction, and real browser behavior.

### Current Test Coverage

- **Unit tests**: Comprehensive coverage of individual modules
- **Integration tests**: 40 HTTP-level tests using mock OIDC provider and direct API calls (`oauth2_passkey_axum/tests/integration/`)
- **Security tests**: 43 consolidated security scenario tests (`oauth2_passkey_axum/tests-security/`)
- **E2E tests** (Phase 1): 4 Playwright tests covering passkey register/login and OAuth2 popup login (`tests-e2e/`)

### Gap (areas E2E exercises that HTTP tests cannot)

- WebAuthn JS APIs: `navigator.credentials.create/get`
- Signal APIs: `signalAllAcceptedCredentials`, `signalUnknownCredential`
- FedCM: `navigator.credentials.get({ identity: ... })`
- Popup window + `postMessage` flow used by the OAuth2 popup
- Conditional UI / autofill on the login page

### Considerations

- WebAuthn/Passkey requires browser-level testing (virtual authenticator)
- Chrome DevTools Protocol supports virtual authenticator for testing
- Playwright + Chrome's CDP virtual authenticator works (proven in Phase 1)
- WebAuthn rejects IP-literal origins → must use `localhost`, not `127.0.0.1`
- CI integration requires headless browser support
- Test infrastructure adds TS/Node to a Rust workspace

## Approach

Playwright + TypeScript with Chromium's CDP virtual authenticator
(`WebAuthn.addVirtualAuthenticator`). A standalone `mock-oidc` workspace
member serves as the OIDC IdP so flows can run without external Google
endpoints. Tests target `demo-both` running on `localhost`.

Phase 1 (committed): foundation + smoke + passkey + OAuth2 tests.
Phase 2 (pending): expanded coverage, CI integration, brittleness
mitigations.

## Decision Log

### 2026-02-26: Migrated from ToDo.md

- Context: Migrating incomplete tasks from ToDo.md to issue tracking system

- Reason: Significant infrastructure investment; current integration tests provide good coverage. Worth doing eventually but not urgent

### 2026-05-12: Phase 1 completed

- Context: Manual regression testing on `demo-live` after each change had become a bottleneck; only happy-path flows were verified.
- Decision: Adopt Playwright TS + Chrome CDP virtual authenticator. Build a standalone `mock-oidc` binary for deterministic OIDC. Use `demo-both` as the system under test.
- Reason: Playwright Rust bindings are immature; TS is the de-facto path. CDP virtual authenticator handles passkey flows without real hardware. Standalone mock keeps E2E offline-deterministic.
- Outcome: 4 tests pass in ~6s (smoke ×2, passkey register-then-login, OAuth2 popup login). `mock-oidc` mirrors `axum_mock_server.rs`; consolidation deferred to Phase 2.
- Surprises: WebAuthn rejects IP-literal origins (must use `localhost`); `/o2p/user/logout` only redirects when `?redirect=` is supplied; new-user OAuth2 triggers passkey promotion popup (disabled for now via `O2P_PASSKEY_PROMOTION=disabled`).

### 2026-05-12: Phase 2 completed

- Context: Phase 1 left state isolation, admin/conditional-UI/FedCM coverage, and selector stability as follow-ups. Each test currently shares process state via the in-memory SQLite, which made per-test isolation the unlock for adding the remaining flows.
- Decisions:
  - **Per-test DB reset** — added a `test-reset` Cargo feature on `oauth2-passkey` (and pass-through on `oauth2-passkey-axum`) that exposes `reset_storage_for_test()`. `demo-both` mounts `POST /test/reset` when `DEMO_BOTH_TEST_RESET=1`. Playwright calls it from a `resetDb()` helper at the top of each spec. The function cascade-deletes users and resets SQLite autoincrement sequences so the next inserted user lands at `sequence_number=1` again (admin bootstrap depends on this).
  - **`data-testid` rollout** — login buttons, conditional-UI link, account-page actions, admin user rows, force-logout button, and the dynamically-injected passkey registration modal now carry stable `data-testid` attributes. Existing specs were refactored to use them.
  - **FedCM coverage at the HTTP API layer**, not via the browser FedCM dialog — `navigator.credentials.get({ identity: ... })` needs a real Google config endpoint reachable from the browser, which CI cannot provide. Added `POST /test/issue_token` to `mock-oidc-core` that mints a JWT signed by the same key the JWKS endpoint advertises. The spec drives `/oauth2/fedcm/nonce` → token mint → `/oauth2/fedcm/callback` end-to-end (token signature, issuer, audience, and nonce all validated by the library; happy-path creates a session, negative path rejects wrong nonce).
  - **`O2P_FEDCM=enabled` set globally for the suite** — needed for the FedCM routes to mount. Existing OAuth2 spec falls back to the popup flow because the browser-side FedCM dialog cannot reach a real config endpoint, so coverage is preserved.
- Outcome: 9 tests pass in ~20s — smoke ×2, passkey register-then-login, OAuth2 popup + promotion-dismiss, account-page add/delete passkey, admin list+force-logout, conditional UI auto-resolve, FedCM positive, FedCM negative. CI workflow already in place from the earlier batch (`.github/workflows/e2e.yml`, `continue-on-error: true`).
- Surprises:
  - SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` does not reset on `DELETE FROM users` — the next inserted user gets `sequence_number=2`, which silently breaks "first user = admin" bootstrap. Fixed by also wiping `sqlite_sequence` in the reset function.
  - `login_history` has no FK to users (audit retention), so it doesn't cascade. The reset path clears it explicitly.
  - All four storage tables live under the configurable `DB_TABLE_PREFIX` (default `o2p_`), not the bare names. The reset SQL has to honour the prefix.
  - Conditional UI auto-resolves on page load with the CDP virtual authenticator's `automaticPresenceSimulation` — no input focus required. Asserting the intermediate URL races against the immediate redirect to `/`; the spec waits on the `/auth/finish` response and the final URL instead.

### 2026-05-13: Phase 3 — demo-app coverage

- Context: Phase 2 covered the library's authentication surface end-to-end against `demo-both`. The remaining gap was the **integrator-facing demos** (`demo-custom-login`, `demo-cross-origin`, `demo-todo`, `demo-profile`). These illustrate library usage patterns that integrators copy; a silent regression on them is invisible to library-level unit tests.
- Decisions:
  - **One spec per demo**: `demo-custom-login.spec.ts` (4 tests, `O2P_LOGIN_URL` redirect contract), `demo-cross-origin.spec.ts` (4 tests, cross-origin cookie + CORS), `demo-todo.spec.ts` (4 tests, 1:N pattern with form-CSRF), `demo-profile.spec.ts` (5 tests, 1:1 pattern). Each demo gets its own Playwright `webServer` entry on a dedicated port.
  - **Per-demo test-reset endpoint** — mirroring `demo-both`'s pattern, each demo's `main.rs` mounts `POST /test/reset` when `DEMO_<NAME>_TEST_RESET=1` is set. `demo-todo`/`demo-profile` additionally wipe their app-specific tables (`todos`, `user_profiles`).
  - **Postgres dependency for demo-todo / demo-profile**: those demos hard-code `sqlx::PgPool`. Local devs run `docker run -d --rm --name e2e-pg ...`; CI declares `services: postgres` in `.github/workflows/e2e.yml`. A `globalSetup` does a TCP reachability check and fail-fasts with a remediation hint if the port isn't open.
  - **csrfToken fix in `demo-custom-login/templates/login.j2`** — discovered while writing the spec: the custom login template wired `showRegistrationModal('create_user')` to the JS-injected modal but never defined the `csrfToken` global the library's `passkey.js` references. Result was `ReferenceError: csrfToken is not defined` during registration. Added `const csrfToken = "_NOT_SET_";` to match the library's built-in login.j2.
- Outcome: **38 tests pass in ~1 minute** (smoke ×2 + passkey ×1 + oauth2 ×1 + account-passkey-mgmt ×1 + admin ×1 + conditional-ui ×1 + fedcm ×2 + oauth2-linking-protection ×2 + passkey-registration-protection ×2 + demo-both-protected ×8 + demo-custom-login ×4 + demo-cross-origin ×4 + demo-todo ×4 + demo-profile ×5).
- Trade-off accepted: each demo's `main.rs` now carries ~12-25 lines of test-only code (test_reset handler, conditional route mount, env-var gates). Acceptable as a stepping stone; tracked in `20260513-1356` for a follow-up that pushes this back into the library so the demos can return to their pre-E2E line count.
- Surprises:
  - Playwright runs `globalSetup` **in parallel** with `webServer` entries, not before them. demo-todo's eager `PgPool::connect()` therefore dies with `PoolTimedOut` long before any `globalSetup` orchestration can spawn a Postgres container. `globalSetup` was downgraded to a "verify reachable, fail loud" check, and Postgres pre-start was delegated to the caller (CI services / local `docker run`).
  - `require.resolve('./global-setup')` in `playwright.config.ts` does NOT auto-append `.ts` — must be written `'./global-setup.ts'` explicitly. A wrong path silently disables `globalSetup` with no error.
  - `default-features = false` on `oauth2-passkey-axum` disables the built-in `/o2p/user/login` page. `demo-custom-login` exposes its own `/login`; the spec drives registration through that page instead of the library's built-in one.

### 2026-05-13T15:50 — Correction on the Phase 3 csrfToken note

Above, the Phase 3 decision log records the csrfToken finding as
"discovered while writing the spec ... added `const csrfToken =
"_NOT_SET_";` to match the library's built-in login.j2." That
description is accurate as a *narrative of what was done*, but it
mis-framed the underlying issue as a one-off demo template oversight.
The real bug is library-side: `passkey.js`'s `startRegistration`
unconditionally references the `csrfToken` global even in
`create_user` mode, where the server's AuthUser extractor is `None`
and the CSRF check never runs. Any custom login page that loads
`passkey.js` without declaring `csrfToken` hits a `ReferenceError` —
this is not specific to demo-custom-login, it would silently break
for any integrator building their own anonymous login UI. The
demo-custom-login template patch in 6ae6531 fixes the *symptom* for
that demo (integrator-side correct action under the existing
contract) but does not touch the *root cause*. Tracked separately in
`20260513-1550` with the library-side plan (make the
`X-CSRF-Token` header conditional on `mode === 'add_to_user'`).
**Resolved**: `20260513-1550` landed immediately as planned;
`passkey.js` now gates the header on mode, and both the library's
built-in `login.j2` and `demo-custom-login`'s `login.j2` have had
their `const csrfToken = "_NOT_SET_";` workaround declarations
removed. The 38-spec suite still passes.

### 2026-05-13: Phase 3 cleanup (follow-up to 20260513-1356)

- Context: Phase 3's commit left each demo's `main.rs` carrying 12-25 lines of test-only code (`test_reset` handler, conditional route mount, env-var gates). Tracked in `20260513-1356`; landed immediately after.
- Decisions:
  - `POST /o2p/test/reset` moved into `oauth2-passkey-axum/src/router.rs` behind the existing `test-reset` Cargo feature. Each demo's `Cargo.toml` now declares a passthrough `[features] test-reset = ["oauth2-passkey-axum/test-reset"]`; Playwright opts in via `cargo run -p <demo> --features test-reset`. Without the flag the route is not compiled — the demo source carries zero test wiring.

- Outcome: 38 tests pass in ~1.7 min, **no Postgres required at any layer** (local or CI). Demo `main.rs` line counts return to within 1-6 lines of pre-Phase-3 (residual is doc comments on the new SQLite default).

### 2026-05-13: Planned — rename `test-reset` → `e2e-test`, gate dotenv with `#[cfg]`

- Context: After the Phase 3 cleanup the only test-only Rust still in
  demo `main.rs` files is a runtime `DEMO_*_SKIP_DOTENV` env-var
  check. The matching env var is set by Playwright config (5 places)
  to keep the workspace-root `.env` from leaking into the test
  environment. The runtime check is dead code in production builds
  (the env var is never set there) and has nothing to do with how
  modern Rust gates compile-time behaviour.
- Plan:
  1. Rename the Cargo feature from `test-reset` to `e2e-test` across
     `oauth2-passkey`, `oauth2-passkey-axum`, all 5 demos, and every
     reference (Playwright config, CI workflow, README, closed issue
     `20260513-1356` doc). The widened scope (E2E-build flag, not
     just a reset entry-point) is reflected in the name.
  2. Replace `if std::env::var("DEMO_*_SKIP_DOTENV").is_err() {
     dotenv().ok(); }` (3 lines) in each demo's `main.rs` with
     `#[cfg(not(feature = "e2e-test"))] dotenv().ok();` (2 lines).
     Drop the `DEMO_*_SKIP_DOTENV: '1'` entries from the Playwright
     config (5 places) and the "Known gotchas #5" note from
     `tests-e2e/README.md`.
- Trade-off: production builds can no longer flip dotenv off via
  env var. Acceptable — that flexibility was never exercised; demos
  always want dotenv in release. The compile-time gate communicates
  intent more honestly ("this is a non-test build only").
- Why not file a separate issue: this is a sub-1-commit refactor and
  the parent E2E-tests issue is the right home for the Decision Log.
  (Lesson learned from `20260513-1356`, which retrospectively could
  have been a Timeline entry here from the start.)
