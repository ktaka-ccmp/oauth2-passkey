## Description

Add browser-level end-to-end tests that exercise the full authentication flow including JavaScript execution, DOM interaction, and real browser behavior.

### Current Test Coverage

- **Unit tests**: Comprehensive coverage of individual modules
- **Integration tests**: 40 HTTP-level tests using mock OIDC provider and direct API calls (`oauth2_passkey_axum/tests/integration/`)
- **Security tests**: 43 consolidated security scenario tests (`oauth2_passkey_axum/tests-security/`)
- **E2E tests** (Phase 1): 4 Playwright tests covering passkey register/login and OAuth2 popup login (`tests-e2e/`)

### Gap (areas E2E exercises that HTTP tests cannot)

- WebAuthn JS APIs: `navigator.credentials.create/get`
- Signal APIs: `signalAllAcceptedCredentials`, `signalUnknownCredential`
- FedCM: `navigator.credentials.get({ identity: ... })`
- Popup window + `postMessage` flow used by the OAuth2 popup
- Conditional UI / autofill on the login page

### Considerations

- WebAuthn/Passkey requires browser-level testing (virtual authenticator)
- Chrome DevTools Protocol supports virtual authenticator for testing
- Playwright + Chrome's CDP virtual authenticator works (proven in Phase 1)
- WebAuthn rejects IP-literal origins → must use `localhost`, not `127.0.0.1`
- CI integration requires headless browser support
- Test infrastructure adds TS/Node to a Rust workspace

## Approach

Playwright + TypeScript with Chromium's CDP virtual authenticator
(`WebAuthn.addVirtualAuthenticator`). A standalone `mock-oidc` workspace
member serves as the OIDC IdP so flows can run without external Google
endpoints. Tests target `demo-both` running on `localhost`.

Phase 1 (committed): foundation + smoke + passkey + OAuth2 tests.
Phase 2 (pending): expanded coverage, CI integration, brittleness
mitigations.

## Decision Log

### 2026-02-26: Migrated from ToDo.md

- Context: Migrating incomplete tasks from ToDo.md to issue tracking system
- Decision: Create as low-priority, large-difficulty issue
- Reason: Significant infrastructure investment; current integration tests provide good coverage. Worth doing eventually but not urgent

### 2026-05-12: Phase 1 completed

- Context: Manual regression testing on `demo-live` after each change had become a bottleneck; only happy-path flows were verified.
- Decision: Adopt Playwright TS + Chrome CDP virtual authenticator. Build a standalone `mock-oidc` binary for deterministic OIDC. Use `demo-both` as the system under test.
- Reason: Playwright Rust bindings are immature; TS is the de-facto path. CDP virtual authenticator handles passkey flows without real hardware. Standalone mock keeps E2E offline-deterministic.
- Outcome: 4 tests pass in ~6s (smoke ×2, passkey register-then-login, OAuth2 popup login). `mock-oidc` mirrors `axum_mock_server.rs`; consolidation deferred to Phase 2.
- Surprises: WebAuthn rejects IP-literal origins (must use `localhost`); `/o2p/user/logout` only redirects when `?redirect=` is supplied; new-user OAuth2 triggers passkey promotion popup (disabled for now via `O2P_PASSKEY_PROMOTION=disabled`).

### 2026-05-12: Phase 2 completed

- Context: Phase 1 left state isolation, admin/conditional-UI/FedCM coverage, and selector stability as follow-ups. Each test currently shares process state via the in-memory SQLite, which made per-test isolation the unlock for adding the remaining flows.
- Decisions:
  - **Per-test DB reset** — added a `test-reset` Cargo feature on `oauth2-passkey` (and pass-through on `oauth2-passkey-axum`) that exposes `reset_storage_for_test()`. `demo-both` mounts `POST /test/reset` when `DEMO_BOTH_TEST_RESET=1`. Playwright calls it from a `resetDb()` helper at the top of each spec. The function cascade-deletes users and resets SQLite autoincrement sequences so the next inserted user lands at `sequence_number=1` again (admin bootstrap depends on this).
  - **`data-testid` rollout** — login buttons, conditional-UI link, account-page actions, admin user rows, force-logout button, and the dynamically-injected passkey registration modal now carry stable `data-testid` attributes. Existing specs were refactored to use them.
  - **FedCM coverage at the HTTP API layer**, not via the browser FedCM dialog — `navigator.credentials.get({ identity: ... })` needs a real Google config endpoint reachable from the browser, which CI cannot provide. Added `POST /test/issue_token` to `mock-oidc-core` that mints a JWT signed by the same key the JWKS endpoint advertises. The spec drives `/oauth2/fedcm/nonce` → token mint → `/oauth2/fedcm/callback` end-to-end (token signature, issuer, audience, and nonce all validated by the library; happy-path creates a session, negative path rejects wrong nonce).
  - **`O2P_FEDCM=enabled` set globally for the suite** — needed for the FedCM routes to mount. Existing OAuth2 spec falls back to the popup flow because the browser-side FedCM dialog cannot reach a real config endpoint, so coverage is preserved.
- Outcome: 9 tests pass in ~20s — smoke ×2, passkey register-then-login, OAuth2 popup + promotion-dismiss, account-page add/delete passkey, admin list+force-logout, conditional UI auto-resolve, FedCM positive, FedCM negative. CI workflow already in place from the earlier batch (`.github/workflows/e2e.yml`, `continue-on-error: true`).
- Surprises:
  - SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` does not reset on `DELETE FROM users` — the next inserted user gets `sequence_number=2`, which silently breaks "first user = admin" bootstrap. Fixed by also wiping `sqlite_sequence` in the reset function.
  - `login_history` has no FK to users (audit retention), so it doesn't cascade. The reset path clears it explicitly.
  - All four storage tables live under the configurable `DB_TABLE_PREFIX` (default `o2p_`), not the bare names. The reset SQL has to honour the prefix.
  - Conditional UI auto-resolves on page load with the CDP virtual authenticator's `automaticPresenceSimulation` — no input focus required. Asserting the intermediate URL races against the immediate redirect to `/`; the spec waits on the `/auth/finish` response and the final URL instead.
