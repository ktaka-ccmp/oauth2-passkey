## Description

Add configurable rate limiting to protect authentication endpoints from brute-force attacks and abuse. Currently there is no built-in rate limiting -- this responsibility falls entirely on the deployer (reverse proxy, WAF, etc.).

### Endpoints That Need Protection

- `POST /o2p/passkey/auth/start` and `/finish` -- Passkey authentication
- `POST /o2p/passkey/register/start` and `/finish` -- Passkey registration
- `GET /o2p/oauth2/google` -- OAuth2 login initiation
- `GET /o2p/user/csrf_token` -- CSRF token generation
- `POST /o2p/admin/*` -- Admin operations

### Considerations

- Should be optional (not all deployments need library-level rate limiting)
- Per-IP and per-user rate limits
- Configurable windows and thresholds
- Should work with both in-memory and Redis cache backends
- Must not add significant latency to normal requests
- Should integrate with login history for failed attempt tracking

## Related Issues

- `2026-02-08-02` Login History DB Spam Risk from Brute-Force Attacks (related; rate limiting would mitigate this)

## Approach

Implement as an optional middleware with configuration via environment variables. Consider using a token bucket or sliding window algorithm backed by the existing cache store.
